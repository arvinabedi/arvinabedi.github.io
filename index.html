01 Internal platform toolhub.ronixtools.com

Eight tools the team never had, and the platform to run them.Ronix Tool Hub · Aug–Oct 2026 · sole builder, from blank repo to production

ProblemProduct cards, labels, QR codes, catalog sheets, infographics and landing pages were made by hand, one at a time, by whoever had time in the branding team. Every request queued behind a designer, every output looked slightly different, and nothing was logged or repeatable.
ConstraintIT had no Node experience and there would be no cloud. So: one server, one SQLite file, an idempotent setup script with eight self-checks, and an install manual a non-technical admin can finish in thirty minutes.
BuiltEight production tools, written from scratch: Persian and English product-card generators, a carton-label generator, a QR generator, a one-page catalog designer, a landing-page editor that keeps every version, and an infographic designer with a translator that rebuilds the same picture in another language. Every PDF comes out in CMYK, ready for the printer. Then the platform they live in: one login, owner/admin/user roles with per-person tool access, invite-only onboarding, searchable run history, HTTPS via nginx, and a push to main goes live in about two minutes. It is also the sign-in for the company's other internal apps: Content OS, PDMS and the DAM.

03 Information architecture 82 shares · 36 servers

4.2 million files, finally findable.Branding archive programme · Aug–Sep 2026 · crawl to runbook

ProblemFifteen years of design work across 82 network shares. No product had a home: one drill's assets were spread over 32 shares. A folder called video existed at seven different depths, and the approved files sat deepest of all.
MeasuredA read-only crawl of everything reachable: 193.4 TB, 4.23 million files. Thirty percent duplicate. 4,134 paths longer than Windows allows. The product code buried in 41% of paths turned out to be the join key for the whole archive.
DecidedSix top folders, four levels, every folder name owned by exactly one level, a 53-term controlled vocabulary, and a filing rule that needs no judgement call. Then an executive deck to get it signed off, and a migration runbook that never deletes anything.

04 Analytics + local LLM 29,000 issues

Found the 37% of time when nothing was happening.Jira pipeline analytics · 2026 · Python, SQLite, Ollama

ProblemManagers asked "why are we late?" and Jira could not answer. Issues closed the same day; products still took months. Jira's own links were unused, so nothing connected one product's graphic, content, filming, packaging and publish steps.
Found41% of issue summaries carry a product code. Reconstructing each product's chain from that code showed a median 70 days per product, of which 25.8 days nobody had any issue open. The worst bottleneck was photography, the oldest unfinished step on 280 of 702 open products. Invisible in Jira, because it happens between tickets.
BuiltA manager-facing dashboard plus an assistant you ask in plain English. Counts always query live Jira; diagnoses must cite the measurement behind every claim. A regression test checks that every percentage in an answer appears verbatim in the evidence, after an early version claimed 90% where the truth was 55%. Runs on a local model because the data cannot leave the network.

The parts of Tool Hub that took real engineering: a catalog tool that reads the website and refuses to print bad data, a deploy loop with no pipeline, and access that seals itself.

A Catalog page designer

It reads the website, then refuses to print bad data.

A one-page catalog used to mean retyping specs off ronixtools.com. The designer syncs a product range straight from the live site into a local cache, converts every image to a 300-dpi TIFF for print, and runs a gate before anything reaches a page: images that go soft past 65 mm, products with no spec table, labels misspelled on the site. Nothing is guessed around. Blockers come back as a list a person decides on, so a wrong value never reaches the printer.

B Deploy loop

No pipeline, no cloud. The server pulls.

The company firewall blocks port 22 and there is no CI runner. So the server does the pulling: every two minutes a cron job checks main over SSH on port 443, takes a lock, builds, and restarts the service. One log to watch. The database lives outside the app folder, so a deploy can replace the whole app without touching an account. The first release ran on Windows Server with a PowerShell installer that runs eight checks and is safe to run twice. The move to Ubuntu kept the rule: anyone can redeploy, nothing can half-deploy.

C Accounts & roles

Access that seals itself.

The first visit to /setup creates the one administrator, and then that page stops existing, so nobody can wander in later and make themselves admin. Everyone after that arrives by invite, mailed through the company's Exchange relay, with a generated password they must change on first sign-in. Three roles decide who runs tools, who edits the library, and who manages people. Passwords are scrypt hashes, sessions live server-side and can be revoked, and every run is logged with who, what, and when.

I learn how the team actually does the job before I touch a spec: who waits on whom, where the files live, what the Friday panic looks like. The product brief comes out of that, not out of a backlog.

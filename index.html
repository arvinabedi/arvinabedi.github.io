01Internal platform

Tool Hub

Aug–Oct 2026 · built alone, from an empty repo to production

The branding team made every dealer card, carton label, QR code, catalog sheet, infographic and landing page by hand in Illustrator, one at a time. Requests waited for whichever designer was free, no two outputs quite matched, and nothing was recorded.

I replaced that with eight tools and the web app they live in. You sign in once, pick a tool, fill in a form or drop in a spreadsheet, and get a print-ready CMYK PDF. Roles and per-person access decide who sees what, every run is kept so it can be made again, and the same login now opens Content OS, PDMS and the DAM.

IT had never run a Node app and there was no cloud budget, so it's deliberately small: one Linux server, one SQLite file, a setup script that's safe to run twice, and a manual a non-technical admin can follow in half an hour. Over six weeks I merged 49 pull requests. A push to main is live about two minutes later.

How three parts of it work

The catalog designer checks the data before anything prints

A one-page catalog used to mean retyping specs off ronixtools.com. Now the designer syncs one product range from the live site into a local cache and converts every image to a 300-dpi TIFF. Then it checks everything before a page is laid out. Problems come back as a list for a person to decide on; nothing gets guessed around. On the first real range, 84 products out of 2,017, it caught:

  • Images below print resolution (the site only stores 768 px, which goes soft past 65 mm)24
  • Products with no specification table8
  • Products with no feature bullets7
  • Spec labels misspelled on the website (fixed in the cache, original kept)6
  • Accessory lists with no separators (stored whole, never split by guesswork)3

Deploying without a CI pipeline

The company firewall blocks port 22 and there's no CI runner, so the server does the pulling. Nothing ever reaches in from outside. The database lives outside the app folder, so a deploy can replace the whole app without touching a single account.

  • git push origin mainfrom my laptop; nothing else to click
  • */2 * * * * ~/toolhub-poll.shevery two minutes the server asks GitHub for changes
  • flock ~/toolhub-deploy.locktwo deploys can never overlap
  • git pull via ssh.github.com:443port 22 is blocked on the corporate network
  • npm run buildlogged to one file
  • systemctl --user restart toolhubnginx in front, restarts itself on failure

Accounts and roles

The first visit to /setup creates the one administrator, and after that the page stops existing, so nobody can come along later and make themselves admin. Everyone else joins by invite, with a generated password they change on first sign-in. Passwords are scrypt hashes, sessions are kept on the server and can be revoked, and every run records who, what and when.

02Partner-facing

DAM and distributor portal

2026 · product, UX and deployment · built with Sam Mehrany

Approved photos, labels and manuals lived on a NAS two network hops away. Whenever a distributor needed a file they emailed the brand team, and nobody could say for sure which version was the approved one.

We built one library with five roles. Staff upload files, tag them against a controlled vocabulary and approve them. A distributor types a product code and downloads exactly the files their store needs, and only files someone has explicitly cleared for partners.

Before release I went through it as a hostile user and logged thirty problems, three of them serious, each with evidence and a fix. Then I captured every screen as every role, 47 in all, so the next release had something to compare against.

Distributor portal. One search box: a product code goes in, that store's photos, labels and manuals come out.

03Information architecture

Archive restructure

Aug–Sep 2026 · crawler, analysis and the new structure

Fifteen years of design work sat across 82 network shares. One drill's files were spread over 32 of them, a folder called video existed at seven different depths, and the approved files were usually the deepest of all.

I wrote a read-only crawler and ran it over everything: 4.23 million files, 193.4 TB. About 30% was duplicated, 4,134 paths were too long for Windows, and a product code appeared in 41% of paths. That code turned out to be what could tie the whole archive together.

The new structure has six top folders and at most four levels, down from fifteen, a 53-term vocabulary, and a filing rule that needs no judgement calls. Management signed it off from a short deck, and the migration runbook never deletes a file.

04Analytics, local LLM

Jira pipeline analysis

2026 · Python, SQLite, Ollama · built with Sam Mehrany

Managers kept asking why products shipped late, and Jira couldn't tell them. Individual issues closed within a day, yet products took months, and nothing linked one product's design, copy, filming, packaging and publishing tasks together.

41% of issue titles contain a product code, so we used it to rebuild each product's chain from 29,000 issues. The median product took 70 days, and for 25.8 of them no issue was open at all. The most common hold-up was photography, the oldest unfinished step on 280 of 702 open products, and it never showed up in Jira because it happened between tickets.

Managers get a dashboard and an assistant they can ask in plain language. Counts come from live Jira, and every claim in an answer has to cite the number behind it. A regression test checks that each percentage appears in the evidence; we added it after an early version said 90% when the real figure was 55%. It runs on a local model because the data can't leave the company network.
